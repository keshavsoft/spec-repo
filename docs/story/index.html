The Story of spec-repo

How a quest for zero-overhead, declarative UI generation sparked the separation of HTML blueprints from compiler engines.

The Core Philosophy

Decouple tag design from the compiler engine. Your DOM specifications should be pure, serializable JSON—free of imperative JavaScript logic, runtime dependencies, or template string chaos.

Chapter 1: The Imperative Trap

In modern web development, generating dynamic tables, forms, and select inputs typically forces a painful compromise:

  • Heavy Virtual DOM Frameworks: Shipping megabytes of runtime libraries just to render structured tabular data.
  • Messy Template Literals: String-concatenating HTML strings (`<tr><td>${val}</td></tr>`), creating brittle escaping bugs, missing closing tags, and zero static validation.
  • Imperative JavaScript Builders: Nesting dozens of document.createElement() and element.setAttribute() calls that marry UI appearance directly into business logic.

Whenever designers wanted to adjust a table's padding class or change an input type, they had to open complex JavaScript compiler files. There was no single source of truth.

Chapter 2: The Declarative Revelation

The breakthrough came with a fundamental question: What if an HTML structure was simply a pure JSON data structure?

Instead of writing code that creates a tag, what if we define the tag as pure data: 

{
  "tagName": "th",
  "textContent": "${columnName}",
  "attributes": {
    "class": "py-3 px-3 fw-semibold text-uppercase small"
  }
}

Notice what happened:

  1. Zero Runtime Dependencies: It is just JSON. It can be stored in a file, fetched over an API, cached, versioned, or generated dynamically.
  2. Dynamic Interpolation Tokens: ${columnName} and ${rowValue} act as declarative placeholders waiting for live data hydration.
  3. Complete Engine Agnosticism: Any compiler engine—such as spec-to-dom, json-to-dom, or json-to-tag—can ingest this blueprint and assemble native DOM elements.

Chapter 3: The Triad Architecture (Tags + Instructions + Definitions)

As the system scaled to enterprise dashboards, a tag blueprint alone was not enough. Real-world applications need to know where to place rows, how to iterate through collections, and how to compose complex widgets.

This led to the canonical 3-tier architecture found in spec-repo today:

🏷️
1. Tags & Spec
The atomic HTML building blocks (spec.json / tags.json). Defines tags, attributes, and text tokens.
⚙️
2. Instructions
The assembly directives (instructions.json). Maps source data paths to target DOM paths via JSONPath queries.
📦
3. Definitions
High-level component recipes (definitions.json). Bundles base templates with instruction lists and feature toggles.

Chapter 4: The Evolution Across 17 Iterations

spec-repo did not happen overnight. Its version history (from v1 through v17) reflects deep real-world battle-testing:

  • v1 – v5: Focused on basic table rows and column sizing specifications.
  • v6 – v12: Introduced data-role query selectors, footer aggregations, and datalist autocompletion.
  • v13 – v16: Modularized specifications into discrete units (table.json, select.json, dataList.json, form.json).
  • v17 (Current): Unified instruction engine with JSONPath selectors (jsonpathly), pluggable feature options (serial numbering, actions column, search bar), and global registration support.

Chapter 5: What Lies Ahead

Today, spec-repo serves as the foundation for high-performance data grids, form generators, and micro-frontend architectures. By keeping specifications clean, declarative, and decoupled, developers can build reactive, beautiful web interfaces at maximum speed and minimal bundle size.
